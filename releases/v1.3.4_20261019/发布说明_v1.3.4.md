## 为什么会提前响（查出两个原因，都会造成这个现象）

### 原因一：**「空闲」不等于「干完了」**

应用内部对 agent 的状态是这么判的：

> 状态 = 「空闲」或「**维护中**」→ 报告为**空闲**；否则报告为「跑着」

**维护也报成空闲** —— 而「压缩上下文」「溢出恢复」这类维护，正是**一轮任务干到一半**时跑的。于是任务干到一半，应用发了一次「跑着 → 空闲」，我们就响了一声；等它真干完（1~2 分钟后）又响一声。这跟你说的「过一两分钟才结束」完全对得上。

（应用自己的开发文档里甚至写着：要等 `turn/end` 这种"落地事件"，**不要拿 agent 状态当完成信号**。）

### 原因二：**这个信号是所有任务的，不只你等的那一个**

子任务、别的会话干完了也报「空闲」→ 我们响了，可你等的那件事还在跑。

## 现在的三道防线

| | 做法 | 挡住什么 |
|---|---|---|
| **A** | 认出「维护中的假空闲」，当没发生 | 压缩上下文那一下 |
| **B** | **按任务分别记账**：谁在跑记着谁，只有**所有任务都不在跑**才算一次完成 | 子任务先完就响 |
| **C** | 全部空闲后**再等 3 秒**，这期间谁又跑起来就取消 | 短促抖动 |

## 验证

新写了个**真跑的功能测试**（把主机端真正挂上去的那个监听函数抓出来，按真实顺序喂事件），12 项全过：

- 任务干到一半跑压缩 → **不响**；真干完才响；同一件事只响一次；
- 主任务 + 子任务：子任务先完**不响**，两个都完才响；
- 空闲一下又跑起来（抖动）→ 取消不响，真安静下来才响；
- 刚启动就来的空闲 → 不算完成。

另有 6 项守着这三道防线不许被改回去。全套 **14 个脚本**退出码全 0，版本对账三处全对。
