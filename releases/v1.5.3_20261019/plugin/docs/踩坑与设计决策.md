## 一、这插件是什么

DeepSeek Harness 桌面端的换肤插件。干四件事：

1. **换背景图** —— 全屏壁纸，横图铺满 / 竖图原图显示 + 两侧模糊过渡
2. **自动配文字色** —— 按图片明暗判黑白字，保证文字在背景上看得见
3. **悬浮球 + 面板** —— 右下角（现为输入框上沿）一个圆形入口，点开是图库和设置
4. **任务完成提示音** —— 内置合成音 + 自定义音频

**架构是两半**：

| 半边 | 文件 | 职责 |
|---|---|---|
| 主机端 | `plugin/index.js` | 开本机 HTTP 接口，把设置/图库/图片/音频存成文件 |
| 页面端 | `plugin/client.js` | 改主题 token、画壁纸、渲染悬浮球和面板 |

**为什么必须主机端存盘**：桌面版每次启动换一个随机端口，浏览器里的 localStorage 跟着换地址就作废 —— 作者刚设的背景一重启就没了。走文件才留得住。

**接口清单**（都在 `/dsh-skin/` 下）：

| 路径 | 用途 |
|---|---|
| `state` | 读/写设置（`{method:"set", patch:{}}`） |
| `library` | 图库增删改查、批量重算 |
| `image?id=xxx` | 取图片本体（原图 / `&thumb=1` 缩略图） |
| `diag` | 页面端自检结果回传通道 |
| `bell` | 任务完成信号（页面每秒来问一次） |
| `sounds` | 自定义音效增删查 |
| `sound?id=xxx` | 取音频本体 |

## 二、根因分类（视觉问题翻来覆去就这几类）

作者一天报了十几轮视觉问题，归完类就下面这几类。**下次碰到先对这类，别重新查。**

### 0. 先记住一句话：判据和落点是两条路就会出事

下面 4 条里有 3 条本质都是同一件事：**「我以为的背景」和「屏幕上真正的背景」不是同一个值**。
09:5x 补的第 5 条也是它。

### 1. 判黑白字的判据用错字段

**症状**：明显偏亮的图配了白字，字看不见。

**根因**：判亮度用的是图片「主色」，而主色算法挑的是**最饱和**的颜色。有张图最饱和的是暗红发饰（`#401116`），于是被当成暗图配了白字 —— 作者眼睛看到的是整张图的亮堂，不是发饰那块。

**解法**：改用整图平均亮度（`avgLum`），主色只继续负责给底色染色调。

### 2. 保底太厚，背景永远糊一层奶雾

**症状**：透明度拉到 0 还是模模糊糊一层。

**排查过程（这条最值得记）**：先怀疑应用自己的毛玻璃钩子（`--dsw-mask-blur`），grep `app.asar` 确认它**只在弹窗打开时挂上、不压壁纸** —— 排除。最后定位到插件自己的 `PANEL_FLOOR = 0.18`：哪怕滑杆拉到 0，聊天区和侧栏上也永远压着 18% 的白，两层叠一块能到 30%+。

**解法**：降到 `0.06`。

**顺带一个技巧**：查 app.asar 里某个 CSS 变量怎么用，**直接二进制 grep 上下文**（node 读 buffer + `indexOf`），比解包快得多。

### 3. 半透明字判定和显示对不上号

**症状**：一批中等亮度的图，小字对比度 3.3-3.5:1，差一点点不达标。

**根因**：三级文字是 `rgba(...,0.86)`，但判定对比度时拿纯白/纯黑算。屏幕上真正显示的是混过一遍的淡色 —— 判定和显示对不上号。

**解法**：`fixIfBlind` 改成按「混出来的颜色」判，不够先试「去掉透明度」，还不行才推档。

### 4. 图标色跟文字色共用一个判断

**症状**：系统图标变白，压在亮底上直接消失。

**根因**：图标色（`--dsw-alias-menu-icon`）取的是**文字的三级色**。深色图上那枚色是白的，白图标压白底就没了。**文字和图标落点不同** —— 文字在面板里，图标在侧栏/工具栏/菜单，常常是更亮的那块。共用一个判断，必然有一边看不见。

**解法**：图标色从**真正写进去的菜单底色**反推（见下面 08:55 定稿）。

**这条是通用教训：颜色不能因为「都是前景色」就共用一个判断。**

#### 07:15 第一次修 —— 没修到根上

改了图标色，但**没管图标背后的底衬**，而且判据只看 `PANEL_LAYER` 一层。图标实际落在侧栏（`sidebar-fill`）、二级面板（`bg-layer-2`）这些层上 —— 那些层还是白的。拿一层的明暗判所有层的图标色，必然对不上。作者 08:03 重启后还是看不见。

#### 08:03 第二次修 —— 反而刷出了一块白

改了两处：图标色按「所有底衬里最亮那层」判 + 侧栏那层「压暗一档」。

**结果第二处是反的。** `veilBaseFor(..., wantsWhite=false)` 在黑字档返回的是**浅色主题的近白**，我却按「压暗」的意图垫了 82% —— 刷出一整块白底衬。**作者 08:45 说的「白色充填底衬」就是它。**

#### 08:45 第三次修 —— 三个错叠在一起

1. 侧栏 82% 白垫（上面那条）→ **撤掉**
2. 判出黑白后又过 `fixIfBlind`，它拿**壁纸**当基准比对比度，把黑图标推成白图标
3. **手动档那段老代码在后面又覆盖了一遍图标色**（按 palette 判）—— 上面算对了，下面给盖回去。这是「白图标压白底」的直接原因

#### 08:55 定稿

查应用文档确认：`Menu icons use --dsw-alias-menu-icon` —— 这枚色**专门给菜单图标和导航箭头**用，图标就坐在菜单那层上。

**所以从真正写进去的菜单底色反推**：底亮 → 黑图标，底暗 → 白图标。判据和落点从此不可能不一致。图标色**只留一处来源**，不再走 `fixIfBlind`。

**实测**：菜单图标 `#1a1c20` vs 菜单底 `#fff` → **对比度 17.06:1**。`full_verify.cjs` 里加了硬判据：图标 vs 菜单底 < 3:1 直接判失败。

**三条教训**：
- **判据不该「另算一遍背景」** —— 算出来的和真正写进去的是两条路，中间任何不一致（主题取不到、兜底值不同）都会让两者对不上。**直接读写好的那个值。**
- **同一个 token 在多处赋值 = 定时炸弹** —— 后设的覆盖先设的，改漏一处就白改。两处都在设图标色，就是这次找不到真凶的原因。
- **改前景色时先问「它落在哪些背景上」**，只看一层背景就是漏修。

### 5. 不透明的实色底根本没进清洗名单（10-19 09:5x 补）

**症状**（作者原话）：「系统标识有白色底的，里面文字看不到。对话内容中有白色底色的有的看的到，有的看不到。」

**为什么「有的看的到、有的看不到」**：清洗名单是按 **token 名**一枚一枚列出来的（`SURFACE_LAYERS`），列到的洗了 → 看的到；没列到的原样留成白的 → 字被刷成白的 → 看不见。同一个界面上两种表现，根因就一个。

**查法（可复用）**：把 `app.asar` 里的主题表抠出来，解析 `var()` 链，筛「**不透明 + 偏亮**」的底色 token，再跟插件的清洗名单对差集。
脚本：`verify/wash_audit.cjs`（抠表 + 对差集）、`verify/scan_all_defs.cjs`（全量扫写死的色值）。

**结果**：差集 21 枚，其中 19 枚是「不透明实色底」，另外 2 枚是菜单那两层半透底。**全库 1387 张里有 345 张（24.9%）走白字档 —— 这些图下每一个没洗的实色底都是白压白。**

**修法（两种底、两套办法）**：

| 底的类型 | 例子 | 办法 |
|---|---|---|
| **不透明实色底** | 行内代码、标签、引用块、文件差异行、回到底部那颗圆钮、卡片上的按钮 | 进 `SOLID_FILLS` 表：**白字档写应用深色主题那枚色、黑字档写浅色那枚色** |
| **半透底（带毛玻璃）** | 菜单材质 `--dsw-menu-surface-fill`、菜单吸顶分组条 | 加进 `SURFACE_LAYERS`，照旧走垫底那套（浓度还归作者那根滑杆管） |

**三个关键判断**：
1. **实色底不走垫底那套**。「垫一层半透底、让壁纸透出来」的模型对不透明实色底不成立；而且应用自己就有深色主题的同名值 —— 直接用它的，观感跟应用原生深色主题一致，颜色语义也不跑（文件差异行的绿/红就是这么保住的，中性黑垫底会把色相洗掉）。
2. **两档都要写死**。字色档由「壁纸亮不亮」定，跟「应用现在是浅色还是深色主题」无关；只写一边，另一边（比如深色主题 + 亮壁纸）就会黑字压深底。
3. **菜单图标读错了 token**。08:55 读的是 `--dsw-specific-menu`，可菜单材质那层（`._material`）真正用的是 `--dsw-menu-surface-fill` —— 前者只是后者的别名。**判据读「我以为的那层」，屏幕上是「真的那层」**，还是那两条路。这两枚现在都洗、读哪枚都一样，但优先读真正用的那枚。

**顺手拆掉的一个陷阱**：`veilBaseFor` 原来是 `rawToken('dark') || rawToken('light') || 兜底` —— 深色值取不到时会**退到浅色值**（近白）。真机上内置主题两张 token 表是空的，所以一直走兜底、看不出问题；哪天有主题注册了浅色 token，白字档就会拿到**白的底**。**垫底色不许跨档回退**，改掉了。

**教训**：
- **清洗名单是「按名字列举」的，就一定会有漏网的**。改完拿 `app.asar` 反查一遍差集，是这个插件以后每轮都该跑的。
- **别只看前景色，先问「这个界面上还有哪些底不是我的」**。
- 验证脚本里手抄常量 = 报告骗人：`blue_band_audit.py` 里写死了「wash 锁 0」，于是它永远算不出蓝字档；实际 `effectiveWash` = 自动底线（0~20%），亮图能垫到 11%。已换成 `verify/ink_band_audit.cjs`（常量全部从源码抠）。

#### 13:2x 补刀：还有一种底「连 token 都不是」——组件自己的局部变量

作者红框圈出来的是消息里那张**交付文件卡片**（白底、写着文件名的那张）：浅色壁纸下黑字看得见，深色壁纸下字刷成白的、卡片还是白的。

**量的数（`verify/measure_card.py` 直接量作者给的两张截图）**：

| 截图 | 卡片底色 | 卡里字的颜色 | 对比度 |
|---|---|---|---|
| 深色壁纸（外滩夜景） | `#f4f4f4` | 找不到比底色更深的像素 → 就是白字 | **≈1.0 : 1（看不见）** |
| 浅色壁纸（对照） | `#f8f8f8` | `#181c20`（黑字） | **16.13 : 1（正常）** |

**根因**：这张卡的底不是 alias token，是组件自己的一枚局部变量：

```
.xxx_root{ --deliverable-fill: var(--dsw-static-neutral-50) }    ← 指到静态色板
.xxx_file{ background: var(--deliverable-fill) }
body[data-ds-dark-theme] .xxx_root{ --deliverable-fill: var(--dsw-static-neutral-850) }  ← 只有挂那个属性才变深
```

插件既没挂那个属性、又从来没动过静态色板 —— 所以它一直是白的。同样的写法还有三处：`--card-fill`、`--changes-fill`、`--plan-card-fill`（连各自的 `-hover`），一次全治。

**修法**：`STATIC_SURFACE_FLIP` 表，把四枚静态色板按字色档翻：白字档把 `neutral-50/100` 换成应用深色主题的 `neutral-850/800`；黑字档反过来把 `850/800` 换成 `50/100`（治「应用是深色主题 + 亮壁纸」那种反向情况）。四个都写死，两条 `body[data-ds-dark-theme]` 分支就都是对的了。

**为什么敢翻静态色板**（查过 `app.asar`，引用面极窄）：

| 静态 token | 全应用引用 | 都是些什么 |
|---|---|---|
| `--dsw-static-neutral-50` | 6 处 | 上面四张卡的 fill + 行内代码（已在 `SOLID_FILLS` 里） |
| `--dsw-static-neutral-100` | 4 处 | 四张卡的 hover 底 |
| `--dsw-static-neutral-850` / `-800` | 6 / 4 处 | 同上，深色那侧 |

**一处当字色/图标色用的都没有** —— 翻它不会误伤前景。反过来 `--dsw-static-neutral-00` **绝对不能碰**：它既当 40×40 图标格那种半透白底，又当 SVG 里那些白色填充，翻它会把 logo 洗黑。

**为什么不是给 body 挂 `data-ds-dark-theme` 一把梭**：那枚属性是应用的 ThemePresenter 自己管的，每次主题快照变更它都按「应用当前是什么主题」重设/移除 —— 而插件写一次 token 就会触发一次快照变更，挂了也立刻被抹掉。而 presenter 把 token 写成 **body 的内联样式（优先级最高）**，所以走 token 这条路既稳又不用跟它抢。

**新增脚本**：`static_surface_audit.cjs`（找出所有「拿静态色板当底」的地方）、`theme_apply_probe.cjs`（查静态色板取值 + presenter 把 token 写在哪）、`measure_card.py`（直接量作者截图上的卡片颜色，修前取证用）。

### 第三版：切块面积占比（现在用的）

- 黑块明显多 → 白字
- 白块明显多 → 黑字
- 差不到 5% → 灰块自己偏哪边定夺

**踩的两个坑**：

**坑 A：切块统计不能用 WCAG 相对亮度。** 第一版用 WCAG + 0.05 黑块界，拿夜景实测**暗块占比 0%**，79%~90% 全掉进灰块 —— 白切了。WCAG 那把尺是给算对比度用的，它把中暗色调得太亮；人眼看夜景的深蓝天空明明就是黑的，它却算成中间色。
**改回 sRGB 感知亮度（0-1），黑块界 0.35 / 亮块界 0.65**，夜景立刻判对。

**坑 B：量图必须量原图，不能量截图。** 一开始量的是作者给的截图，两个错：① 屏幕上每个像素都已经垫过底，亮度被抬过；② 截图里混着界面元素，裁错地方（裁到水面）结论直接反。找原图靠 `verify/landscape_contact.py` 拼联系表肉眼认。

## 六、静默失败：同一个坑踩了三次

这是**最贵的一类 bug**，因为作者要重启才发现，而且验证脚本还会报绿骗我。

### 事故 1（23:18）：选图片没反应

**现象**：作者重启后点任何一张图，界面毫无变化。
**根因**：`buildTokens` 里 `const band` 被挪到了 surfaces 之后才声明，而 surfaces 里用到了它。JS 的 const 有「暂时性死区」，提前引用抛 `ReferenceError`，外层的 try/catch 又把它吞了 —— **token 一次都没写进去，换肤静默失败**。

### 事故 2（00:40）：改蓝字档又栽一次

同一个模式：`wantsWhite` 写在第一个 `if (entry)` 块里，第二个块用不到。

### 为什么之前没发现

1. `node --check` 只查语法，**「变量挪位置」这种错它查不出来**
2. 验证脚本当时还写着「全部无异常」—— 它只统计异常条数，没检查「到底写没写进去」

### 补的两道防线（都在，别删）

1. `refreshLayer` 的 catch **不再静默**，异常打到控制台
2. `full_verify.cjs` 加硬判据：**有底图却一次 token 都没写 → 直接判失败，不许报绿**。已实测：故意注入崩溃时它会红，修好后它绿

### 通用教训

- 凡是「没反应/没变化」这类报告，**先怀疑静默异常，别先怀疑视觉效果**
- **根因是同一个模式：变量被「后来的新用法」拖着挪位置。改这种多处共用的变量，一开始就声明在最高层。**

## 七、其他翻车记录

### 大小上限共用一个数，把音频卡死（01:00）

**现象**：自定义音效「添加不上去」，页面既收不到成功也收不到失败。
**根因**：主机端读请求体的上限是 `MAX_IMAGE_BYTES`（24MB）。音频走 data URL 会被 base64 撑大三分之一，再套一层 JSON —— 上限卡太死，音频稍大请求就被掐断。
**解法**：读体上限单独放大到 64MB（`MAX_BODY_BYTES`），真正的大小校验交给各自的处理函数按类型判（音频 8MB、图片 24MB），`decodeDataUrl` 支持传上限。**失败原因现在显示在面板上，不再静默。**

**教训：一个常量被两种不同的文件类型共用，就是这类 bug 的温床。按类型分上限，别共用一个数。**

### 中文注释被 PowerShell 啃了（11:02，最惨的一次）

**现象**：434 处中文注释和界面文案损坏，75 处把相邻两行黏成一行，插件加载不了。
**根因**：用 PowerShell 的 `Get-Content / Set-Content` 改文件。中文版 Windows 的 PowerShell 读文件默认按 GBK 读，而文件是 UTF-8 —— 一个 UTF-8 文件被当成中文读一遍又写回，中文全被啃了。

**铁律：编辑 `client.js` / `index.js` 只能用 edit/write 工具或 Node，永远别用 PowerShell 的文本 cmdlet。**

### 竖图完全看不到图（18:15）

**根因**：CSS 绘制顺序里，负 z-index 的元素画在 canvas（html 背景）**之上**。原来主图挂 html 背景，模糊垫底层（`z-index:-2`）盖满全屏、几乎不透明 —— 主图一出生就被垫底盖死了。横图没有垫底层所以正常，这也解释了「明度怎么调都没用」：调的是内容层，看不见的那层根本没参与。
**解法**：主图改成独立元素 `.dsh-skin-front`（`z-index:-1`）。

### 打开面板不定位当前图（19:15 修了一半，22:05 才发现）

作者报「现在并不是」。**三个洞叠一起**：
1. 图库分页加载（一次 60 张），当前图排在几百名开外时**压根没被画出来**，`findIndex` 拿 -1 直接 return → `page` 改 `useMemo`，当前图不在已加载页就补进去
2. 滚动框自己没设 `position`，格子的 `offsetTop` 参照外面某一层，**算出来的 scrollTop 是错数** → 滚动框设为定位祖先
3. 刚打开那一帧格子还没排完版 → 定位函数跑两遍，开后 60ms 再定一次

### 面板打开时内容跳一下（19:15）

`scrollIntoView` 会连外层面板一起滚 → 改成直接算 `scroller.scrollTop`。

### 换图要等十几秒

图库 1387 张，一次性全画出来每换一张图就要重画 1387 个缩略图 → **分页一次 60 张**，滚动时用 `IntersectionObserver` 看哪些格子进了可视区，只给这些真的去加载图片。

### 文字阴影把界面卡死（23:08）

第一版用「给 body 增删 class」开关光晕 —— 那个 class 一加一删就改动全应用所有元素的文字渲染，叠上换图时的重绘，界面直接卡住不响应。作者报「选了图片直接没反应」。
**解法**：不碰 DOM，直接拼进那份壁纸样式里跟着整体替换；选择器用 `:where(body)`（零特异性，应用的样式照样压得过它）。

### 弹窗不够毛玻璃（18:40）

应用本来就留了两枚钩子，之前一个没用上：`--dsw-menu-backdrop-filter`（默认 blur 40px）、`--dsw-mask-blur`（默认 `none`，等于没开）。两枚开足。

## 十三、音效批量添加 + 容量上限（10-19 13:55，作者选的 B 案）

作者原话：「音效支持批量添加，目前最大支持多大的文件，总文件多大？评估过了吗？」

**查出来的三件事**（改之前）：

| 问题 | 当时是什么样 |
|---|---|
| 批量添加 | **不支持**：选文件框没开 `multiple`，代码只取 `files[0]` —— 框选 10 个只进去第一个，**另外 9 个一声不响地没了**（静默丢文件，跟 23:18 那类同族） |
| 单文件 | 8MB，页面 + 主机两端都拦（约 128k mp3 八分半 / 未压缩 wav 57 秒） |
| 总量 | **一条上限都没有**（没条数、没总字节），加到磁盘满为止；这项之前没评估过 |
| 顺带查出 | `postJson` 在 `!ok` 时抛 `host responded 400`，**把主机端写的那句人话扔了** |

**怎么改的**：

- 选文件框开多选；整批**逐个上传**（一个文件一个请求，免得一次请求把 64MB 读体上限撞了）；加完给一句汇总，**没进去的原因分开列**（格式不对 / 超 8MB / 条数满 / 总量满 / 主机端没收）。
- **两道闸在主机端写盘之前拦**（权威），页面本地也预判一道（大文件不白传）。
- 索引新增 `bytes` 字段；老索引没记的去 `stat` 一次文件 —— 否则总量算成 0，闸门形同虚设。
- 覆盖同一条（同 id）时先把旧的占用减掉，不然改个文件也撞墙。
- 面板加一行「容量：已用 xMB / 上限 200MB · n/30 条（单个最大 8MB，可一次多选）」。
- 顺手修的三处：① `postJson` 把主机端的人话透传出来；② 主机端单文件超限以前走 `decodeDataUrl` 返回 null 只报 `bad sound`，现在先按读体上限解出来再单独判 8MB，报的是「单个音效最多 8MB」；③ **`soundsCache` 是模块级变量，重新装配不清就会一直用上一轮的旧列表** —— 现在每次 `apply` 从盘上重读。

**功能测试（不是读关键字）**：`verify/sound_quota_check.cjs` 把主机端真的跑起来（假 `webServer` + 假 req/res），13 项全过：单个超限拦住**且文件没落盘**、第 31 条拦住、总量超拦住（报的已用数对得上 197.0MB）、覆盖同一条能过、删掉一条 usage 跟着降、回话带 usage。
`sound_check.cjs` 第 ⑩ 节 13 项，其中一条专门盯「**页面和主机端那三个数不许漂**」。

**教训**：**「静默丢文件」跟「静默吞异常」是同一类毛病** —— 用户以为做了操作、系统啥也没说。凡是「一次收多个」，先问「多出来的那些去哪了」。

## 十六、透明度放开 0~40% + 提示音「一次都没响过」的真凶（10-19 19:1x）

作者原话：「透明度你应该调整到 0~40%。另外，你检查一下，为什么任务完成了不触发声音提示。」

### ① 上限 25 → 40（**两个文件必须一起改**）

页面的 `MAX_WASH` 和主机端写盘前那道夹取，原来各写了一个 25。只改一处就会出现「拖到 40 → 存进去被夹回 25 → 下次打开自己弹回去」这种**看着像滑杆坏了**的现象。

现在主机端也提成常量 `MAX_WASH = 40`，并加判据盯两边不许漂（`sound_quota_check.cjs` 第 ⑧⑨ 节：数值一致 + 真机写读 `40/999/0`）。

### ② 提示音的真凶：同一个接口的两个分支回**不同形状**的数据

```
页面：postJson(BELL_PATH, {})        →  POST
主机：if (req.method === 'POST') { ... return { ok: true } }   ← 没有 at！
      return { at: lastDoneAt, kind }                          ← 只有 GET 才有
```

页面那句 `Number(result?.at) || 0` 于是**恒等于 0**，「时间戳变了没有」永远不成立 → **内置叮和自定义音效一次都没响过**。

**为什么一直没被发现**：试听是页面自己直接播的，绕过这条路 —— 现象就成了「试听能响、任务完成不响」，看着像"开关没打开"，其实是协议对不上。

**修法（两头都改，跨版本也对得上）**：页面改用 `getJson(BELL_PATH)`（**问数据就用 GET**）；主机端 POST 也把 `at`/`kind` 一起回。

**教训：同一枚接口，两个 method 分支回不同形状的数据 = 定时炸弹。** 调用方只走其中一条分支，另一条分支的空字段就永远发现不了 —— **必须两条都打一次**（这就是 ⑦ 节的测法）。

### ③ 作者还要做两件事，提示音才响

开关**默认关**（他 23:45 定的「默认关」）—— 要先打开；再点一次 **试听**（浏览器要求页面先有一次用户点击才允许出声）。这两条**不是 bug**，是设计 + 浏览器的规矩。


| 时刻 | 主机 at | 页面判断 | 结果 |
|---|---|---|---|
| 第 1 次问（刚启动） | 0 | `at > 0` 不成立 | lastBellSeen 仍是 0（**"没见过任何时间戳"**） |
| 第一个任务完成 | T | `at > 0` ✓、`at !== 0` ✓ | 命中「`lastBellSeen !== 0`」→ **不响**，然后把 lastBellSeen 记成 T |
| 第二个任务完成 | T2 | 同上，但 lastBellSeen 已非 0 | 响了 |

**现象**：每次重启后**第一个任务永远不响**，第二个才开始响。作者重启后只跑了一个，所以看着像"开关根本没接上"。

**为什么会写成这样**：本意是「主机端可能留着插件启动前那次完成的旧时间戳，别一启动就补响一声」。可主机端**跟应用一起重启、at 从 0 开始**，根本没有旧时间戳 —— **拿「值是不是 0」当「见没见过」用，判的对象错了**。

**修法**：一枚专门的 `bellSeenOnce` 记「基线取过没有」；第一次问到的值（哪怕 0）就是基线，之后**只要变了就响**。问不到数据时**不提前立基线**，下一轮还能补上。

**顺带去掉一处静默**：自定义音效 `play()` 失败原先是 `.catch(() => {})` 吞掉 —— 现象就是"没声音"且查不着。现在退回内置叮 + 面板写一句原因。（这条正是为什么作者「点了试听能响、任务完成不响」时看不出所以然。）

**教训（今天第二次同类）**：**「值是不是 0」和「有没有见过」是两件事**。上午栽的是「被常量锁死的条件 ≠ 没触发」（14 节），这次是「值 0 ≠ 没见过」——**都是拿 A 当 B 用**。凡是靠"哨兵值"表达"没发生过"的地方，都要单独一枚标志。

**新脚本**：`verify/bell_check.cjs`（把 `startBellWatch` 从源码抠出来真跑，4 组场景 10 项：重启后第一个任务就响 / 有旧值不补响 / 开关关着不响 / 选了自定义走自定义那条）。

## 十八、「自动底线」从硬挡降级成建议（10-19 20:3x）

作者原话：「我不是让你把透明度调到 0~40% 吗？为什么是从 9 开始的」

**那个 9 = `autoFloorPct`**：每张图按它最糟的那块地方算出来的「字会看不清的下限」（作者 10-18 21:40 点头过，原话「一起都改」）。它当时被用在**两个地方**：

```js
min: floorPct                                              // 滑杆左端 = 这张图的底线
return clamp(Math.round(Math.max(base, floor)) ...)         // 再把数值抬到线下
```

于是现象是「写着 0~40、实际从 9 拖起」，**作者要的区间根本没落地**；更隐蔽的是它还悄悄改掉了 19:5x 刚定的两个档（休闲 5% 被抬到 9%）。

**改法**：

- 滑杆 `min: 0`（左端就是 0），`setWash` 的夹取也改成 `clamp(值, 0, MAX_WASH)`；
- `effectiveWash` 里**不再 Math.max(…, floor)**：专注 35 / 休闲 5 / 正常按图或手调，原样生效；
- 底线**只剩显示**：滑杆下面一行小字「这张图建议不低于 9%（再低字可能发糊，糊了往右拖两格）」；
- 状态行读数从「自动垫底」改名「**建议最低**」—— 它已经不改任何东西，名字得说实话。

**教训（本日第三次同类）**：**「防呆」和「用户明确要的区间」冲突时，先按用户的话办，再把失去的保护显式说出来。** 不要拿"为你好"偷偷把区间改掉。00:56 → 18:5x → 20:3x 这三轮反复，根子都是**删/挡的时候没把「为什么」和「代价」讲清楚**。

**判据**：`mode_wash_check.cjs` 里「底线 9 时休闲仍是 5 / 正常手调 0 仍是 0 / 专注仍是 35」三连 + `sound_check.cjs` 的「`min: floorPct` 不许回来」「底线不许再抬数值」。

## 十九、提示音「提前响」：空闲 ≠ 干完了（10-19 20:5x）

作者原话：「为什么有的时候任务还没跑完，但是它就已经声音提醒你了。但是基本上过一两分钟任务才结束。这种情况不多见」

**两个原因，都是"拿 A 当 B"**：

**① 维护阶段也算 idle。** 应用里：

```js
get status() { return this.phase.kind === 'idle' || this.phase.kind === 'maintenance' ? 'idle' : 'running' }
```

`maintenance`（压缩上下文、溢出恢复、启动初始化）**报的是 idle**。而压缩正发生在**一轮任务干到一半**时 → `running → idle(维护)` → 我们响了一声；真干完再响一声。应用自己的文档写着「Wait on durable events such as `turn/end` … **Do not poll `agent/status`**」—— 这条信号本来就不是给"完成"用的。

**② 广播是所有 agent 的。** 子 agent、别的会话干完也报 idle → 子任务完就响，主任务还在跑。

**三道防线**（`plugin/index.js`）：

| | 做法 |
|---|---|
| a | `payload.phase?.kind === 'maintenance'` 当没空闲（拿不到这字段也不要紧，有 b/c 兜） |
| b | **按 agent 记账**：`runningAgents` 集合，谁跑加谁、谁空闲摘谁；**集合空了**才算完成 |
| c | 集合空后再等 `bellSettleMs`（默认 3000，可被 config 覆盖以便测试）→ 期间任何一个又跑起来就 `cancelSettle()` |

卸载时也要 `cancelSettle()`（别把定时器留在那儿）。

**判据**：新增 `verify/bell_signal_check.cjs` —— 把主机端真正注册的监听函数**抓出来真跑**，按真机顺序喂事件：维护中不响、子 agent 先完不响、抖动取消、没见过 running 不算完成，12 项全过。`sound_check.cjs` 第 ③b 节 6 项守这三道防线。

**教训（本日第四次同类）**：**「状态变空闲」≠「这件事干完了」**。今天四次全是**拿 A 当 B**：被常量锁死的条件 ≠ 没触发（14 节）／值 0 ≠ 没见过（17 节）／防呆 ≠ 用户要的区间（18 节）／空闲 ≠ 干完（本节）。

**可选的后手**（没做，记在这里）：应用有落地事件 `turn/end`（`ctx.on('session/event', (session, event) => event.type === 'turn/end')`），那才是"一轮真结束"。等哪天 `agent/status` 这条路再出花样，就走它 —— 但得先确认动态包能不能听到 `session/event`（现在没验，不冒险换）。

## 二十、中英双语 + 首次安装指引（10-19 21:2x）

### ① 语言开关

- **位置**：`SkinControls` 的**第一段**（在「恢复默认界面」之前）。实测顺序：语言 → 恢复默认 → 模式 → 背景明度 → 图库 → 竖图铺法 → 提示音 → 读数。

- `dictFor()` 从「跟随应用语言」改成「**面板选择优先**」；原来的按系统语言那套留成 `systemDict()`（现在只是参考，正常不走）。
